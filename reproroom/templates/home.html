Containment drill

Run a deliberately hostile “reproduction”: it steals the environment, reads /proc/1/environ, tries curl | sh, fork-bombs, runs rm -rf ~ and rm -rf /, fills the disk and allocates memory until something stops it.

You see what the attacker observed from inside, and what the host observed from outside, before and after.

How it works

  1. ReadThe issue via the GitHub REST API, read-only.
  2. ExtractThe LLM returns package, reported version, claimed behaviour and the snippet as JSON, validated against PyPI.
  3. Writerepro.py from the snippet. Every line the model adds is marked # added by Repro Room; it must print REPRO: BUG or REPRO: OK.
  4. RunAt the reported and at the latest version, each in its own fresh sandbox: fetch wheels with the network on, then run with the network off.
  5. RepairOnly if the script itself is broken (syntax, a missing helper, an unrelated import), at most twice, all logged.
  6. VerdictDeterministic rules over exit codes, the wall clock, markers and exception types. Not the LLM.
  7. ExplainA plain explanation and a draft maintainer comment you can copy. Nothing is posted.

Containment model

Process isolationUntrusted code never runs in the app process or on the host: each step is a fresh {{ sandbox.cli }}{% if sandbox.oci_runtime %} --runtime {{ sandbox.oci_runtime }}{% endif %} container.
NetworkOff (--network none) whenever untrusted code runs. The fetch step only runs pip download --only-binary=:all:: wheels, no setup.py.
SecretsNo host environment is forwarded; the script sees exactly 5 variables. API keys stay in the control plane.
FilesystemRead-only root, script and wheels mounted read-only, a {{ sandbox.work_tmpfs }} tmpfs work dir that dies with the container.
PrivilegesUser 65534, --cap-drop ALL, no-new-privileges.
Resources{{ sandbox.memory }} memory (no swap), {{ sandbox.cpus }} CPU, {{ sandbox.pids_limit }} processes, {{ sandbox.run_timeout|int }} s wall clock enforced from the host, {{ (sandbox.output_cap // 1024) }} KB output cap.
Lifecycle--rm after every step, verified gone; the job directory is deleted at the end; a startup janitor removes anything labelled reproroom.
